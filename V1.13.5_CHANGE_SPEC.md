# Exvia v1.13.5 change specification

## 1. Formula prefix simplification

- JavaScript formula: `=<script/expression>`
- SQLite scalar formula: `== SELECT ...`
- `==` is parsed before `=`.
- Plain text remains a literal value.

The change applies to Add Field, formula-enabled normal inputs, Edit Row, and Imaginary Field definitions.

## 2. Imaginary Field changes

### Optional expression

An Imaginary Field may have an empty expression. Such a definition creates an Exvia-only manual column and does not modify the underlying JSON schema.

Manual row values are sparse and are persisted with the imaginary definition. A manual value takes precedence over the definition formula for that row.

### Duplicate handling

When a new Imaginary Field uses an existing imaginary column name, Exvia opens a confirmation dialog:

```text
Replace <name>?
No / Yes
```

Replacing keeps existing manual row values. A collision with a real JSON field is rejected.

### Built-in snippet accordion

Six examples are supplied:

1. Normalized PRICE (0–1)
2. Random PRICE from table
3. Budget detector (`PRICE > 50`)
4. PRICE share of table
5. Income / expense label
6. SQLite high-budget label

## 3. Table Undo / Redo

A bounded delta history is owned by `MainViewModel`.

Each history item contains only:

```text
file path
row index
before row (nullable)
after row (nullable)
operation label
```

No complete Table snapshot is retained per operation.

Supported history mutations:

- Append
- Edit
- Delete

Undo/Redo rewrites the underlying row array through the repository and creates a normal GitHub commit. Successful Undo moves the entry from undo→redo. Successful Redo moves redo→undo. A new CRUD mutation clears redo history.

History limit:

```text
1..50
Default = 50
```

Changing/selecting/resyncing files and running a file-level script clears history.

## 4. Files → SQLite file scripts

A new File Script manager provides:

- saved script list;
- create/edit/remove;
- Execute;
- collapsed built-in examples accordion.

`FileSqlScriptEngine` creates an in-memory SQLite `ALL_FILES` table from the selectable JSON files. Every source row carries `__file` and `__row` metadata.

Allowed script shape:

```text
[CREATE TEMP VIEW / DROP VIEW statements]
SELECT ...
```

or a final `WITH ... SELECT`.

The final query result is saved to a user-selected JSON output file. Internal `__file`/`__row` columns are removed from output.

`-- @exact-schema` activates schema verification for files referenced in a `__file IN (...)` clause.

Built-in examples:

1. exact-schema two-file merge;
2. all-file union;
3. large expense extraction;
4. daily totals;
5. category totals;
6. description keyword export.

Saved scripts synchronize to `.exvia/file-scripts.json`.

## 5. Settings / synchronization

New setting:

```text
display.undo_history_limit
```

The synchronized `.exvia/.exvia-settings.json` display block includes `undoHistoryLimit`, and its resources block references `.exvia/file-scripts.json`.

The PAT remains local/encrypted and excluded from repository configuration.

## Patch — field removal operations

### Real JSON field removal

Table now shows `− Remove field` below `+ Add field`.

1. User selects one of the current real/core JSON keys.
2. Exvia counts rows containing that key.
3. A confirmation dialog explains whether the operation is local-only or destructive to the selected repository JSON.
4. If persisted rows contain the key, `MainViewModel.removeField()` creates row maps without the selected key and writes them through the existing repository `replaceRows()` boundary.
5. Cache/table state is refreshed from the committed result and CRUD undo/redo history is cleared because this operation can modify many rows at once.

### Imaginary field removal

Table now also shows `− Remove imaginary field` below `+ Add imaginary field`.

1. User selects an imaginary field definition.
2. Exvia asks for confirmation.
3. The definition and its sparse manual values are removed.
4. `imaginary-fields.json` is persisted/synchronized through the existing Settings ViewModel flow.
5. The selected Financial JSON is not modified.

The pre-existing remove control in the Imaginary Fields manager remains available.
