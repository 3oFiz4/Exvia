# Exvia v1.13.4 change specification

## Scope

This is an architectural/feature increment over v1.13.3. Existing table, statistics, plotting, GitHub, filtering, flagging, pagination, and MVVM behavior is retained unless explicitly described below.

## 1. Report target configuration removed

- Remove the report-target input/setting from the Settings UI.
- Do not expose a Set Target Repo action.
- Reports always target `<configured-owner>/Exvia`.
- The report classification and GitHub labels remain `#bug`, `#ench`, and `#feat`.

## 2. Filtering and Flagging snippet auto-save

Custom Filtering Snippets and Flagging Methods are persisted locally immediately and, when GitHub credentials are available, synchronize immediately to dedicated files:

```text
.exvia/filtering-snippets.json
.exvia/flagging-snippets.json
```

Delete/edit/toggle operations follow the same rule. GitHub failure does not undo the already-saved local edit.

Color Mapping follows the same dedicated-resource behavior at `.exvia/color-mappings.json`.

## 3. Imaginary fields

### Semantics

An imaginary field is an Exvia-only column definition.

- It is never written into the selected Financial JSON file.
- Evaluation starts from the real/core `TableData`.
- Exvia creates an effective table clone containing the core keys plus active imaginary fields.
- A field value is inserted into a row only if evaluation produces a nonblank value.
- An imaginary field is included in the effective key list only when at least one row contains a nonblank result.
- Core row `originalIndex` values are retained, so CRUD continues to address source JSON rows correctly.
- Filtering/Flagging/Color Mapping and Stat receive the effective table clone.
- CRUD writes use core table data and never serialize imaginary columns.

### UI

Add beside `+ Add field`:

```text
+ Add imaginary field
```

Imaginary field column headers use the current UI `Primary` color.

Settings → Schema & Display includes an Imaginary Fields manager for create/edit/enable/disable/delete.

### Persistence

Definitions auto-save to:

```text
.exvia/imaginary-fields.json
```

## 4. Excel-like formulas

### Input forms

Formula handling is available in:

- normal inferred form fields;
- Add Field's optional starting value;
- Add Imaginary Field's value/formula;
- Edit Row inputs.

Each relevant input has a compact `ƒx` control at the right edge.

### Literal values

Any value without a recognized formula prefix remains a literal string and follows the previous behavior.

### JavaScript

Prefix:

```text
=``
```

Example:

```javascript
=`` Number(row.PRICE || 0) * 1.11
```

The pre-warmed WebView evaluates JavaScript in batches. Exposed values/modules:

```text
row, table, field, index, context, jsonFile,
d3, Plot, aq, theme, helpers
```

No Promise/async formula output is accepted.

### SQLite-style scalar formulas

Prefix:

```text
=SQL:
```

Supported structure:

```sql
SELECT <column|literal> [WHERE <Filtering expression>]
```

Examples:

```sql
=SQL: SELECT PRICE
=SQL: SELECT 'review' WHERE PRICE >= 50000
```

The WHERE matcher reuses Exvia's existing safe Filtering parser. It is not an arbitrary SQL mutation engine.

### Imaginary formulas

Imaginary definitions accept literal, JavaScript, or SQLite scalar content. Each definition is evaluated against each core row. Blank output leaves the imaginary key absent from that row.

## 5. `.exvia/` repository layout

All Exvia-owned customization metadata is separated from Financial data:

```text
.exvia/
├── .exvia-settings.json
├── filtering-snippets.json
├── flagging-snippets.json
├── color-mappings.json
├── custom-metrics.json
├── custom-plots.json
└── imaginary-fields.json
```

The PAT is excluded from all synchronized files.

Resource mutations auto-save their dedicated file. Save settings and reload writes `.exvia/.exvia-settings.json` and reconciles every custom resource file.

## 6. MVVM boundaries

- `FormulaSupport` belongs to domain/service and owns prefix parsing plus SQLite scalar evaluation.
- `ImaginaryFieldDefinition` belongs to the domain model.
- `MainViewModel` owns the core/effective TableData split and imaginary overlay application.
- `FieldFormulaEngine` is the presentation/WebView execution boundary for JavaScript formulas.
- `SettingsViewModel` owns local + GitHub persistence of custom resources.
- `MainActivity` remains responsible for input/dialog rendering and delegates table state/persistence to ViewModels.
