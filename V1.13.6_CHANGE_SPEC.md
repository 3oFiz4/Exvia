# Exvia v1.13.6 change specification

v1.13.6 extends the v1.13.5 MVVM project without changing the core Financial JSON workflow. The release focuses on reusable scripting state, automation, schema-driven inputs, custom-script organization, and Table UI management.

## 1. Exvia ENV variables

Exvia now has an application JavaScript environment named `ENV`. It is an Exvia data structure, not the Android/Linux process environment and not a `.env` file.

Variables are managed under **Settings → Automation & ENV → Variables / ENV**. Each variable has a JavaScript initializer and a persisted JSON value. The runtime exposes explicit CRUD-style methods:

```javascript
ENV.budget.get()
ENV.budget.get('daily')
ENV.budget.post(value)
ENV.budget.put(value)
ENV.budget.put('daily', 60)
ENV.budget.delete('daily')
```

Scripts can also create/update ENV values at runtime. Runtime changes are returned to Kotlin, persisted locally, and synchronized to `.exvia/environment-variables.json` when repository configuration is available.

ENV is available to custom plots, custom metrics, field/imaginary-field JavaScript, schema rules, notification rules, metric-color rules, and supported Filtering/Flagging/File-SQL expressions through `ENV.<name>.get(...)` substitution.

Five built-in ENV examples are supplied: budget, alerts, rolling window, category targets, and profile.

## 2. Shared Custom Accordions

Custom Plot and Custom Metrics now share script groups called **Custom Accordions**.

- `Default` always exists and cannot be deleted.
- Existing scripts from previous versions migrate to `Default` automatically.
- Groups can be added, renamed, or removed.
- Removing a group moves its scripts back to `Default` rather than deleting scripts.
- Inside a shared group, Plotting scripts are shown first and Metrics second.

Group definitions synchronize to `.exvia/script-groups.json`.

## 3. Event notification automation

Settings now contains **Automation & ENV → Notifications**. A notification rule is a JavaScript program bound to one predefined event:

```text
event.amend
event.resync
event.save
```

Scripts can use:

```javascript
event
jsonFile
metric('Mean')
metric('STDV')
ENV.budget.get('daily')
```

A successful rule returns an object such as:

```javascript
return {
  notify: true,
  severity: 'red',
  title: 'Unusual expense',
  body: 'Recent expense is outside the expected range.'
};
```

The Android notification layer is deliberately thin; decision logic remains in the JavaScript rule engine. Android 13+ notification permission is requested when needed.

Built-in examples cover amend confirmation, budget threshold, re-sync, settings save, and a ±2 standard-deviation expense warning.

Notification definitions synchronize to `.exvia/notification-rules.json`.

## 4. JavaScript key-schema rules

**Settings → Schema & Display → Key schema scripts** can modify how dynamic form inputs behave without hard-coding a schema in Kotlin.

A schema script may return:

```javascript
{
  DEFAULT_VALUE: '0',
  HIDDEN: false,
  NUMBER_ONLY_KEYPAD: true,
  PLACEHOLDER: '0 or 1',
  AUTO_COMPLETION: false,
  AUTO_COMPLETION_PARSING: 'uppercase',
  BOOLEAN_01: true
}
```

The evaluator exposes the current key, rows/table, current row context, theme helpers, and ENV. The supplied `is_*` / `has_*` example renders a numeric `0/1` input and converts the submitted value to a boolean-style `true`/`false` value before persistence.

Schema rules synchronize to `.exvia/schema-rules.json`.

## 5. Stateful Custom Metric inputs

A custom metric can now return a metric plus UI-input metadata:

```javascript
return {
  label: 'Daily Budget / period',
  value: budget * period,
  inputs: [
    {name:'period', label:'Period', placeholder:'days', default:'30'},
    {name:'budget', label:'Budget', placeholder:'amount', env:'ENV.budget.daily'}
  ]
};
```

Input values persist automatically. Leaving the Stat page does not discard them. An input may bind to an ENV path; changing the input then updates that ENV value as well.

Four built-in input-metric examples are included. Saved values synchronize to `.exvia/custom-metric-inputs.json`.

## 6. Metric Color Mapping

**Settings → Schema & Display → Metric Color Mapping** adds JavaScript rules keyed by metric name (or `*`). A rule can conditionally return colors for both the metric key and metric value:

```javascript
const n = Number(metric.value);
return {
  key: n < 0 ? theme.negative : theme.positive,
  value: n < 0 ? theme.negative : theme.positive
};
```

Rules apply to statistical, finance, and custom metrics. Default metrics now use red/green semantic coloring rather than the older mixed static palette. Expense-burden finance metrics default toward red; healthy/positive outcomes default toward green. User metric-color rules override defaults.

Metric-color rules synchronize to `.exvia/metric-color-mappings.json`.

## 7. Table focus mode

Table now has **Hide input controls / Show input controls**. Hiding controls removes the dynamic input form, Fields/Imaginary Fields controls, Amend, Undo, and Redo while leaving filtering/flagging and the table itself available.

This is intended for a larger read-only table viewport without altering data or configuration.

## 8. Field managers

The previous separate Add/Remove buttons are replaced by two managers:

```text
Fields
Imaginary fields
```

Each manager displays the current fields in one list. `+ Add` creates a field and the `×` action on each list item removes it after the existing confirmation rules.

- Real-field removal alters the selected Financial JSON.
- Imaginary-field removal only removes the Exvia overlay definition/manual values.

## 9. `.exvia/` resource layout

v1.13.6 adds the following synchronized resources to the existing Exvia workspace:

```text
.exvia/
├── .exvia-settings.json
├── filtering-snippets.json
├── flagging-snippets.json
├── color-mappings.json
├── custom-metrics.json
├── custom-plots.json
├── file-scripts.json
├── imaginary-fields.json
├── script-groups.json
├── environment-variables.json
├── notification-rules.json
├── schema-rules.json
├── metric-color-mappings.json
└── custom-metric-inputs.json
```

The GitHub PAT remains outside synchronized configuration.

## 10. Architecture

The v1.13.2 MVVM separation remains in place. New Android-specific execution wrappers live in `presentation/`, while persistent definitions remain in domain/settings models and repository synchronization remains behind `ConfigurationRepository`.

New presentation components:

```text
presentation/notification/NotificationDispatcher.kt
presentation/plot/FieldSchemaEngine.kt
presentation/plot/MetricColorEngine.kt
presentation/plot/NotificationScriptEngine.kt
```

The shared pre-warmed WebView JavaScript runtime remains the execution environment for JavaScript customization and plotting.

# v1.13.6 stabilization patch

This is intentionally not a version bump.

## A. Kotlin Regex compilation fix

Regex initializers in `MainActivity.kt` that represent `ENV.<name>.get(...)` use Kotlin raw strings (`"""..."""`) so regex escapes such as `\.` and grouping syntax are not interpreted as invalid Kotlin string escapes.

## B. Custom Stat replaces duplicated Plot/Metric settings

There is one developer setting:

```text
Custom Stat
├── Available modules
├── + Built-in metric examples
├── + Built-in plot examples
├── Custom Accordions
├── + Default
├── + <user group>
│   ├── # Plotting
│   └── # Metrics
├── + Plot
└── + Metric
```

Only one `Custom Accordions` manager button exists.

Existing plot/metric definitions keep their `groupId`; previous definitions therefore migrate without changing their resource format. Definitions without a usable group continue to resolve to Default through the existing group normalization behavior.

## C. Stat hierarchy

Custom group names are interpreted as paths separated by `::`.

```text
Stat+::Finance
```

renders as:

```text
Stat+
└── Finance
    ├── # Plotting
    └── # Metrics
```

A group without `::` is a top-level Stat accordion. Custom group roots are siblings of ordinary key accordions and Personal finance. Plots and metrics assigned to the same terminal group render together, Plotting first.

## D. Color Mapping shorthand

Both forms are supported:

```javascript
// compact
table.PRICE.fore = "#f54900"
table.PRICE.back = "#7A1010AA"
table.back = "#3B0A0AAA"

// legacy
table['MATCHING_ROW']['PRICE'].fore = "#f54900"
```

Compact assignments always target rows selected by the rule's associated SQLite-like query. Column lookup remains case-insensitive.

Five compact Color Mapping examples are supplied by `BuiltinExamples.colorMappingRules`.

## E. Metric Color Mapping examples

Built-ins cover:

1. any metric: negative red / positive green;
2. Mean key only;
3. Mean value only;
4. Savings Rate contextual color;
5. Expense Ratio contextual color;
6. Mean trust derived from Mean − Median gap;
7. STDV relative to Mean.

The JavaScript evaluator exposes `metrics(name)` alongside the existing `metric` object, allowing one metric's color to depend on another metric.

## F. Notification Toast

Notification script result objects support:

```javascript
{
  IS_TOAST: true,
  notify: false,
  title: "...",
  body: "..."
}
```

`IS_TOAST` triggers an Android in-app Toast. When `notify` is omitted and `IS_TOAST` is true, the rule is Toast-only by default. Setting both `IS_TOAST:true` and `notify:true` emits both channels.

## G. Faster full settings synchronization

`Save settings and reload` serializes the Exvia workspace resources once and sends them through one repository tree, one commit, and one non-force branch-ref update. This replaces the prior sequential per-resource commit loop. Individual resource auto-saves continue to use their existing isolated save path.

## H. Consistent runtime scaling

`AppFonts` now holds the active runtime text-scale multiplier. Newly created TextViews automatically use it, preventing regenerated table/form/settings views from falling back to their unscaled base size. Existing tree-wide application remains idempotent.

## I. Semantic status line

The status/log line immediately under the title maps message state to:

- Error → red
- Success → green
- Ongoing → yellow
- Info → blue

The mapping is applied whenever the status text changes, including state/effect-driven messages.
